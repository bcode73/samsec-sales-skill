## In Jotform

Jotform payment forms are simpler than dedicated checkout tools (ThriveCart, SamCart) — they're best for collecting straightforward payments, donations, and order forms rather than complex upsell/downsell flows. For full platform help, use `/sales-jotform`.

- **Payment gateways**: 30+ options including Stripe, PayPal, Square, Authorize.net, Venmo, Braintree, Mollie. Connect via Form Builder → Payment tab.
- **One gateway per form**: This is the biggest limitation — you cannot offer both Stripe and PayPal on the same form. Workaround: create two forms or use Jotform's payment method selector widget (if available for your gateways).
- **Product lists**: Add a Product List element with items, images, prices, and quantity selectors. Supports fixed pricing, user-defined amounts (donations), and calculation fields.
- **Subscriptions**: Stripe and PayPal support recurring payments. Configure billing cycle in the payment element settings.
- **Coupon codes**: Add a Coupon field element — configure discount codes, percentage or fixed amount, expiration dates.
- **Order confirmation**: Configure thank-you page redirect and autoresponder email in form settings. Use PDF Editor to auto-generate receipts.
- **Payment form limits**: Free plan allows 10 payment forms, Bronze 100, Silver 250, Gold 1,000. Exceeding the limit blocks new payment form creation.
- **No upsells/downsells**: Jotform has no post-purchase upsell flow. For upsell sequences, use ThriveCart, SamCart, or GrooveSell and embed or redirect from Jotform.
- **No order bumps**: No native order bump checkbox. Workaround: add optional products to the Product List element with clear "Add this too" copy.
- **Mobile**: Jotform payment forms are responsive. For on-site collection, use Jotform Apps in kiosk mode.
- **Testing**: Use Stripe test mode or PayPal sandbox to test payment flow before going live. Submit a test transaction and verify in both Jotform and your gateway dashboard.
- **Best for**: Event registration fees, donation collection, simple product orders, service booking deposits, and any payment collection where a full checkout funnel isn't needed.

## In Builderall (SuperCheckout)

SuperCheckout is the native e-commerce/checkout module inside the Builderall all-in-one suite. For full platform help, use `/sales-builderall`.

- **Order bumps & upsells**: SuperCheckout supports order bumps and post-purchase upsells configured in the UI — attach checkouts to funnel pages built in Builderall's page builders.
- **UI-only — no checkout API**: SuperCheckout has no public API. To react to a purchase programmatically, drive it through **MailingBoss tags** — apply a tag on purchase (e.g. `bought-course`) and trigger the post-sale email automation off that tag.
- **Bundled cost**: included in the Builderall subscription rather than charging a separate per-transaction SaaS fee — attractive for solopreneurs already on Builderall (verify your plan covers checkout/funnels; the funnel builder is gated to a higher ~$79.90/mo tier — pricing best-effort).
- **Reliability caveat**: reviews report periodic SuperCheckout outages (cart/page not loading) — test the full purchase flow before a launch and keep a fallback for time-sensitive sales.
- **Best for**: Builderall users who want checkout, pages, and email in one bill. For dedicated, API-first cart optimization (A/B-testable carts, robust upsell engines), ThriveCart/SamCart are stronger — see their entries and `/sales-checkout` strategy.

## In Paddle (Merchant of Record)

- **MoR checkout, not a conversion-optimizer**: Paddle provides a localized overlay/inline checkout, but its value is being the **Merchant of Record** — it handles global sales-tax/VAT and is the legal seller. Checkout-conversion levers (order bumps, 1-click upsells, A/B-testable carts) are thinner than dedicated carts like ThriveCart/SamCart.
- **Subscriptions + tax built in**: best when you're selling SaaS/digital subscriptions globally and want tax compliance handled — the checkout is one piece of a billing platform, not a standalone cart.
- **API/automation**: client-side checkout via a client token; provision access off **HMAC-SHA256 signed webhooks** (`transaction.completed`, `subscription.activated`). Build on **Paddle Billing** (not legacy Classic).
- **Fee**: ~5% + $0.50/transaction, all-inclusive (global tax included) — higher than a bare processor, in exchange for zero tax ops.
- **Best for**: SaaS/digital businesses selling worldwide that want checkout + subscriptions + tax in one. For Paddle setup/API see `/sales-paddle`; to choose Paddle vs other MoRs see `/sales-merchant-of-record`. For pure cart-conversion optimization, use a dedicated cart instead.

## In ThriveCart

- **Conversion-first cart sold as a lifetime license**: strong order bumps, **1-click upsells/downsells**, A/B-testable carts, abandon-cart recovery, and subscriptions — the dedicated cart creators reach for when they want to own (not rent) high-converting checkout. Standard is **$495 one-time**; Pro+ is **$790 + $295/yr** (the "lifetime" deal is partial — see gating below).
- **Pro+ gating**: affiliate center, sales tax, custom checkout domain, dunning, and advanced reporting are **Pro+ only** ($295/yr) — Standard lacks them. Budget the renewal if you need creator essentials.
- **Automation**: event-driven — **standard webhooks** (all account events) or the **Event Subscription API** (targeted); grant access on `order.success`, revoke on `order.refund`/`order.subscription_cancelled`. **No HMAC** — validate the shared `thrivecart_secret`; dedupe on `order_id`; match offers by numeric product id. REST API (token/OAuth, 60 req/min, PHP SDK).
- **Caveats**: **no download/link protection** (gate files in your own app), and **ThriveCart Learn is deprecated** (→ ThriveAcademy) so don't build new course delivery on it.
- **vs SamCart**: ThriveCart = own-it-forever lifetime; SamCart = $79–199/mo but includes affiliates at base and you keep recurring payments only while subscribed. **Platform skill**: `/sales-thrivecart`.

## In SamCart

- **Conversion-first hosted cart on subscription pricing**: checkout templates, **order bumps + 1-click upsells**, checkout A/B testing, cart-abandonment recovery, **Subscription Saver dunning**, and a built-in **Affiliate Center** — the rent-it rival to ThriveCart's own-it-forever license. Core **$79/mo** vs Pro **$199/mo** (25% off annual), 7-day trial.
- **Pro gating is the catch**: order bumps, 1-click upsells, A/B testing, Affiliate Center, and custom checkout branding all require **Pro** — Core is checkout + courses + AI tools only. Model expected bump/upsell AOV lift against the $120/mo gap.
- **Automation**: **read-mostly REST API** (`api.samcart.com/v1`, `sc-api` key header, official OpenAPI spec — **private beta, key issued by support**) for orders/charges/customers/subscriptions + refund/cancel/scheduleCancel; **Notify URL webhooks** (~15 triggers: checkout charged/failed, product purchased/refunded, subscription charged/failed/canceled/delinquent/recovered, course events) — **unsigned, no documented retries**: tokenize the endpoint URL, verify payloads via the API, keep a polling backup.
- **Caveats**: recurring payment methods **don't port off SamCart** (subscribers must re-consent elsewhere — plan before scaling recurring revenue); billing-after-cancellation is the loudest public complaint, so build self-serve cancellation on `scheduleCancel` + the canceled webhook; products/checkouts are UI-only (no create API).
- **vs ThriveCart**: SamCart = modern templates + ongoing development for $79–199/mo; ThriveCart = $495–790 one-time but affiliate center/dunning/tax are Pro+ ($295/yr). **Platform skill**: `/sales-samcart`.

## In Checkout Page

- **No-code Stripe checkout builder with 0% platform fees, priced by sales volume**: Checkout Page bolts a branded checkout (order bumps, 1-click upsells, cart-abandonment recovery) onto your Stripe account for digital products, subscriptions, payment plans, pay-what-you-want, **and event tickets** — plus standalone form/lead capture. The cheaper, subscription-priced peer to ThriveCart/SamCart; reach for it when a maker wants a fast, API-and-MCP-driven checkout without a lifetime license. **Not a Merchant of Record** — it runs on your Stripe account, so you own tax (Stripe Tax available).
- **Volume-cap pricing, not feature gates**: ~99% of features are on every plan (Launch ~$24/mo annual up to ~$3K/mo sales; Grow ~$83/mo across ~$10K→$100K+ volume tiers; Enterprise custom) — crossing a plan's **monthly sales ceiling** forces an upgrade, so forecast sales, not features. 0% Checkout Page fee (Stripe's ~2.9%+30¢ still applies). Pricing best-effort — verify at checkoutpage.com/pricing.
- **Automation = REST API + conversion webhooks + a native MCP server**: REST at `https://api.checkoutpage.com/v1` (Bearer key, cursor pagination `starting_after`/`ending_before`, **500 req/min store + 100 req/min key** → 429) covering checkout-pages, payments, subscriptions, events/tickets/bookings, customers, forms, coupons, invoices, tax-rates, files. **Webhooks** send a `conversion` event with `object: payment|subscription|submission` — **money is a decimal string** (`"23.99"`, not cents), **no documented HMAC/retries** (tokenize the URL + re-fetch via API to verify, dedupe on `orderId`), and `livemode` separates test from live. Stripe object ids are echoed for reconciliation.
- **Native MCP server for agentic checkout**: `https://mcp.checkoutpage.com` (OAuth, 13 tools) — `claude mcp add --transport http checkoutpage https://mcp.checkoutpage.com`. Because forms + Stripe checkout share one MCP, an AI assistant can build a paid event-registration page (ticket + attendee fields + coupon) end-to-end from a prompt — its standout edge over form-only builders.
- **Caveats**: **Stripe-only** (no PayPal/other gateway), deep design customization is thinner than a full ecommerce platform, and it's not built for large catalogs/inventory. **Platform skill**: `/sales-checkoutpage`; for global tax handled instead, see `/sales-merchant-of-record`.

## In Ecwid

- **Embeddable commerce, not a store builder**: Ecwid (by Lightspeed) drops a full store — catalog, cart, checkout — into any site you already run (WordPress/Wix/Squarespace/custom HTML) via a JS widget, plus a hosted Instant Site. The answer to "add checkout to the site I already rank with" without replatforming. **0% platform transaction fees** on all plans (processor fees apply).
- **Plan gates decide feasibility**: Free = 10 products, **no API, no digital goods, no variations**; Venture (~$29/mo) unlocks digital products + 100 products; Business (~$49) variations + 2,500; Unlimited (~$119). Pricing changed 2026-03 and has risen since the Lightspeed acquisition — verify before recommending.
- **Automation**: REST v3 (`app.ecwid.com/api/v3/{storeId}`, Bearer `secret_*`/`public_*` tokens, **600 req/min per token**, `Retry-After` on 429) + **HMAC-signed webhooks** (`X-Ecwid-Webhook-Signature` = Base64(HMAC-SHA256(`{eventCreated}.{eventId}`, **`client_secret`** — NOT the `secret_*` token)); thin payloads, re-fetch the entity.
- **Caveats**: embedded widget adds JS weight (4s+ product pages in reviews), QuickBooks sync is one-way (inventory doesn't flow back), cancellation flow is friction-heavy, and EU B2B e-invoicing (mandatory Sept 2026) readiness is unconfirmed.
- **vs the field**: Square Online for a free tier + unified in-person inventory; Snipcart for a dev-first JS cart on static/headless sites; Shopify when you're building the store from scratch. **Platform skill**: `/sales-ecwid`.

## In Snipcart

- **A cart you code, not a store you configure**: drop a JS snippet on any static/JAMstack/custom site (Hugo/Gatsby/Next/Astro/WordPress) and define products as `data-item-*` HTML attributes — Snipcart injects cart + checkout. The developer-side answer to "add checkout to what I built"; Ecwid is the widget-store answer for non-coders.
- **Pricing = max(~$20/mo, 2% of sales)** + gateway fees; every feature on the one plan, free forever in Test mode. At volume, compare the 2% against flat-fee carts.
- **The crawler is the security model — and the #1 failure**: checkout validates prices by fetching each `data-item-url` server-side; SPA/headless-CMS pages throw `product-crawling-failed` unless you serve a JSON crawling endpoint or SSR. Four attributes are mandatory (`id/price/name/url`).
- **Automation**: REST API (`app.snipcart.com/api`, **Basic auth — key as username, empty password**), webhooks verified by **token callback** (`X-Snipcart-RequestToken` → `GET /api/requestvalidation/{token}`; no HMAC, no documented retries — keep a polling backup), JS SDK, and an **official hosted MCP server** (~38 tools, `X-Snipcart-Api-Key` header) for Claude Code/Cursor.
- **Synchronous shipping/tax webhooks** run inside the buyer's checkout — endpoint latency = checkout latency. **Platform skill**: `/sales-snipcart`.

## In Foxy

- **Hosted cart/checkout layer with signed products**: add-to-cart links/forms live on your site (Webflow is the flagship pairing), Foxy hosts cart + checkout + receipt. Products are secured by **HMAC link/form signing** (unsigned links let buyers edit `price=`) — the static/CDN-friendly alternative to Snipcart's crawler validation. ~20 years in service; 100+ gateways, any-frequency subscriptions, donations, configurable products.
- **Pricing (best-effort, sources conflict)**: plan fee (entry ~$20–25/mo up to Advanced ~$300/Enterprise ~$2,000) + **1% per transaction, min 5¢, capped ~7.5–35¢ by plan** — the cap beats uncapped 2% carts at real basket sizes. Gateway fees additional.
- **Automation**: **hAPI** — hypermedia REST (OAuth 2.0, HATEOAS link relations like `fx:transactions`, official `@foxy.io/sdk`); **HMAC-signed JSON webhooks** (`Foxy-Webhook-Signature`, hex, raw body) with real retry semantics — **11 retries/hour then auto-deactivation after 12 straight failures**; admin refeed replays missed events.
- **Caveats**: cart/checkout/receipt are Foxy-hosted and styled via template sets (won't match your site untouched — top complaint), dated admin (new beta), second dashboard to run, steep option surface. **Platform skill**: `/sales-foxy`.

## In Shopify

- **Full commerce backend, not a standalone cart**: Shopify owns the storefront, products, orders, customers, AND checkout — a different shape from drop-in carts (ThriveCart/SamCart) that bolt onto an existing site. Pick Shopify when you're running a real store (esp. physical products / DTC); pick a dedicated cart when you just need a high-converting checkout for a course or digital product.
- **Checkout is locked down — and the conversion levers are mostly Plus-tier**: the legacy `checkout.liquid` and "additional scripts" are **deprecated**; checkout changes now go through **Checkout Extensibility** (UI extensions + Functions). **Fully customizable checkout is effectively Shopify Plus**, so on Basic–Advanced you have limited control over the checkout page itself. Shop Pay one-click and Apple/Google Pay are the biggest built-in conversion wins on lower tiers.
- **Order bumps / upsells = apps, not native**: post-purchase upsells and order bumps come from App Store apps (e.g. checkout/post-purchase extensions) rather than a native bump checkbox; budget for an app subscription.
- **Watch transaction fees**: using a **third-party payment gateway** instead of **Shopify Payments** adds a per-sale fee (~2% on Basic, scaling down by tier) on top of card rates — switching to Shopify Payments removes it.
- **Automation**: react to a sale via the **`orders/create` / `orders/paid` webhooks** (verify the HMAC on the raw body) and read/write via the **GraphQL Admin API** — build new integrations on **GraphQL** (REST is legacy as of 2024-10-01). Not a Merchant of Record, so you own tax compliance. **Platform skill**: `/sales-shopify`; to choose a MoR for global tax instead, see `/sales-merchant-of-record`.
- **Best for**: makers/DTC sellers who want a full store + checkout they can automate against. For pure checkout-page conversion on a digital product, a dedicated cart is often simpler.

## In BigCommerce

- **Open-SaaS commerce backend, like Shopify but fee-free on payments**: BigCommerce owns storefront, catalog, orders, customers, and checkout. Its differentiators vs Shopify are **$0 platform transaction fees** on embedded payment providers (using an open/third-party gateway adds a per-GMV surcharge that drops by tier), strong **B2B** (price lists, quotes), and an **API-first/headless** posture. **Not a Merchant of Record** — you own tax.
- **Checkout**: optimized one-page checkout with digital wallets and BNPL built in; deeper customization is via the headless Checkout SDK rather than a native order-bump/upsell checkbox — for those conversion levers you'd add an app or run headless. **Abandoned-cart recovery and customer segmentation are gated above the entry tier.**
- **Automation = REST + thin webhooks**: read/write via the **REST Management API** — most resources are **v3** (`/v3/catalog/products`, `/v3/customers`, `/v3/carts`, `/v3/hooks`) but the classic **Orders API is v2** (`/v2/orders`). Auth is the **`X-Auth-Token`** header on a store-level API account. **Webhooks are thin** — the callback carries only `{scope, store_id, data:{type,id}}`, so you must make a follow-up API call to get the order/product; there's **no HMAC** (secure with a custom secret header) and **no delivery log**, and subscriptions deactivate on repeated 4XX/5XX or inactivity. Rate limit is a per-30-second quota (~150 Standard/Plus, ~450 Pro).
- **Watch for**: a stray **trailing slash returns 403** (as does a missing OAuth scope); budget for the **doubled API usage** every webhook implies. **Platform skill**: `/sales-bigcommerce`; to choose a MoR for global tax instead, see `/sales-merchant-of-record`.
- **Best for**: makers/growing DTC + B2B sellers who want a fee-free, automatable store backend. For pure checkout-page conversion on a single course or digital product, a dedicated cart (ThriveCart/SamCart) is usually simpler.

## In Medusa

- **Open-source (MIT) headless commerce engine you self-host or run on Medusa Cloud**: Medusa owns the storefront, catalog, orders, customers, and checkout in code you control — a developer framework (Node.js/TypeScript), not a turnkey store. **0% GMV/platform fee** on every tier and **no lock-in** (export anytime). **Not a Merchant of Record** — you own tax. Pick Medusa when you want full code-level control and to avoid per-sale fees; pick a hosted SaaS (Shopify/BigCommerce) or a drop-in cart (ThriveCart/SamCart) if you don't want to run infra.
- **Checkout is yours to build**: you build the cart→checkout flow on the **Store API**; order bumps/upsells/A-B-tested carts aren't native checkbox features — you implement them (or wire a dedicated cart in front). Comes with a promotion engine, multi-region/currency, and multi-channel.
- **Automation = REST APIs + an in-code event system, NOT outbound webhooks**: read/write via the **Admin API** (`/admin/...`) and **Store API** (`/store/...`); auth via **JWT Bearer** (from `/auth/{actor}/{provider}`), **admin API key in `Authorization: Basic`**, or **cookie session**; storefront calls need the **`x-publishable-api-key`** header. **There is no outbound-webhook UI** — to notify a CRM on purchase you write a **subscriber** (`src/subscribers/order-placed.ts`, `config.event = "order.placed"`) and make the HTTP call yourself (add your own retries/signing/logging), or install a community webhook plugin. Use the **Redis Event Module** in production (the default Local one loses events on restart).
- **Watch for**: a real dev setup (Postgres + Redis + Node) and learning curve; **v1 vs v2** drift in tutorials/SDKs (v2 = `@medusajs/js-sdk` + `@medusajs/framework`). Pagination is `limit`/`offset` with a `count` total. **Platform skill**: `/sales-medusa`; to choose a MoR for global tax instead, see `/sales-merchant-of-record`.
- **Best for**: developers / GTM engineers / makers who want to own a fee-free, fully customizable store backend and are comfortable running (or paying Medusa Cloud to run) the infra. For a no-code store or a single-product checkout, a SaaS backend or dedicated cart is simpler.

## In Saleor

- **Open-source (BSD-3), GraphQL-first headless commerce you self-host or run on Saleor Cloud**: like Medusa, Saleor owns catalog, channels, checkout, orders, and customers in code you control — a developer platform (Python/Django), not a turnkey store or drop-in cart. **No per-sale fee when self-hosted.** **Not a Merchant of Record** — you own tax (wire a tax app like Avalara via the tax webhooks). Pick Saleor when you want a GraphQL-first backend with **native outbound webhooks** and are comfortable running infra; pick a hosted SaaS (Shopify/BigCommerce) or a drop-in cart (ThriveCart/SamCart) if you don't want to.
- **Checkout is a multi-step GraphQL mutation flow you build**: `checkoutCreate` (keyed by **variant IDs**, not product IDs — variants hold inventory + price — plus a `channel`) → email/address updates → `checkoutDeliveryMethodUpdate` → payment/transaction → **`orderCreateFromCheckout` (requires an APP token)** → `orderMarkAsPaid`. Order bumps/upsells/A-B-tested carts aren't native checkbox features — implement them or wire a dedicated cart in front. Pricing/availability is **per-channel**.
- **Automation = one GraphQL endpoint + native webhooks (unlike Medusa)**: read/write via `https://{store}.saleor.cloud/graphql/` (no REST). Auth is **JWT** — **Users** via `tokenCreate` (short-lived access + refresh), **Apps** via long-lived tokens (most management mutations are app-permissioned); verify against the **JWKS** at `/.well-known/jwks.json`. Saleor **has native outbound webhooks** (sync + async, 160+ events, payloads shaped by a GraphQL `subscription`), so you register a webhook URL on an App — no need to write subscribers like Medusa. Pagination is **Relay cursors** (`first`/`after` + `pageInfo`).
- **Watch for**: webhook **`Saleor-Signature` is JWS RS256 (detached payload) by default; HMAC SHA-256 is deprecated** — verify against the **raw body** (use `@saleor/app-sdk`'s `withWebhookSignatureVerified`); **sync webhooks are on the critical path** (~20s round-trip cap). Self-host needs **Postgres + Redis/Celery + Django**; the **`saleor-platform` repo is dev-only** (not production) and `ALLOWED_HOSTS` misconfig → "Invalid host header". **Saleor Cloud Sandbox is free but non-commercial**; commercial Cloud starts at **Select ~$1,599/mo** (mid-market+ pricing), so the **self-host OSS path is the maker fit**. **Platform skill**: `/sales-saleor`; to choose a MoR for global tax instead, see `/sales-merchant-of-record`.
- **Best for**: developers / GTM engineers who want a GraphQL-first, fee-free, fully customizable store backend with built-in webhooks and will run (or pay Saleor Cloud to run) the infra. Compare with Medusa (Node/REST, no webhook UI) and Vendure. For a no-code store or single-product checkout, a SaaS backend or dedicated cart is simpler.

## In Bagisto

- **Open-source (MIT) Laravel/PHP commerce framework you self-host or run on Bagisto Cloud**: like Medusa/Saleor, Bagisto owns catalog, carts, checkout, orders, and customers in code you control — a developer platform (Laravel + Vue.js by Webkul), not a turnkey store or drop-in cart. **No per-sale/GMV platform fee** (engine is free). **Not a Merchant of Record** — you own tax. Pick Bagisto when your team is on the **PHP/Laravel** stack and wants a fee-free, fully customizable backend (and optionally a multi-vendor marketplace/POS via paid Webkul extensions); pick a hosted SaaS (Shopify/BigCommerce) or a drop-in cart (ThriveCart/SamCart) if you don't want to run infra.
- **Checkout is a multi-step API flow you build**: guest gets a **cart token** (`POST /api/shop/cart-tokens`) → add items → address → shipping method → payment method → place order. Order bumps/upsells/A-B-tested carts aren't native checkbox features — implement them against the cart or wire a dedicated cart in front. Money is a **decimal string in the store currency** (e.g. `"29.9900"`), not cents.
- **Automation = REST + GraphQL, both Shop/Admin split**: REST at `/api/shop/...` + `/api/admin/...`, GraphQL at `/api/graphql` (playground `/api/graphiql`). Auth = public **`X-STOREFRONT-KEY`** (`pk_storefront_...`) on Shop calls + **Laravel Sanctum bearer token** on customer/admin routes (a legacy `bagisto/graphql-api` package uses JWT + `x-app-secret-key` instead — don't mix). REST pagination via `?page=&per_page=` (max 50) with `X-Total-*` headers; GraphQL is Relay cursors.
- **Watch for**: **no native outbound webhooks in core** — react to a Laravel event (`checkout.order.save.after`), poll `/api/admin/orders`, or add a community webhook package (you own retries/signing). Self-host needs **PHP/Laravel + MySQL/MariaDB + Redis + a queue worker**; common footguns are **`APP_URL` mismatch → broken images/mixed content**, **slow first loads** until caches/Redis/queue are set up (bundle-product pricing is a known slow path), and **install permission errors** on `storage/`. **Bagisto Cloud** (Starter/Pro) sells managed hosting — public prices aren't listed (verify live). **Platform skill**: `/sales-bagisto`; to choose a MoR for global tax instead, see `/sales-merchant-of-record`.
- **Best for**: developers / GTM engineers / agencies on the Laravel/PHP stack who want a fee-free, fully customizable, self-hostable store backend (with marketplace/POS options) and will run the infra. Compare with Medusa (Node/TS), Saleor (Python/Django, native webhooks), Vendure (Node/TS), and Sylius (Symfony/PHP). For a no-code store or single-product checkout, a SaaS backend or dedicated cart is simpler.

## In Spree

- **Open-source (BSD-3) headless commerce framework you self-host on Ruby on Rails**: like Medusa/Saleor/Bagisto, Spree owns catalog, carts, checkout, orders, and customers in code you control — a developer framework (Ruby on Rails + a separate Next.js storefront), not a turnkey store or drop-in cart. **No per-sale/GMV platform fee** on the free Community Edition. **Not a Merchant of Record** — you own tax (use Markets tax rules + a tax service). Built for **B2B, multi-vendor marketplace, and multi-store/multi-currency**. Pick Spree when your team is on the **Ruby/Rails** stack and wants a fee-free, fully customizable backend; pick a hosted SaaS (Shopify/BigCommerce) or a drop-in cart (ThriveCart/SamCart) if you don't want to run infra.
- **Checkout = Store API or the shipped storefront**: drive the cart→checkout flow through the **Store API** (`/api/v3/store`, identified by a **publishable key `pk_xxx`** + per-cart **order token**), or use the official Next.js storefront + `@spree/sdk` rather than hand-writing cart calls. Order bumps/upsells are something you build against the cart, not a UI checkbox.
- **Automation = REST (OpenAPI) + native outbound webhooks**: back-office work goes through the **Platform API** (`/api/v2/platform`, **OAuth2 client-credentials** → `POST {store}/spree_oauth/token`, Bearer) or the new open-source **Admin API** (`/api/v3/admin`, **scoped API keys**, since 5.5). Spree **has native outbound webhooks** — register a subscriber (`/api/v2/platform/webhooks/subscribers`, `subscriptions: ["*"]` or e.g. `["order.canceled"]`) and read the **Webhook Events** delivery log to debug. ⚠️ Confirm the current signature/HMAC scheme against live docs before trusting deliveries. Pagination is **JSON:API** (`page[number]`/`page[size]`, follow `links.next`).

## In Drupal Commerce

- **Commerce-as-content on Drupal/PHP — a developer build, not a drop-in cart**: Drupal Commerce (drupalcommerce.org, by **Centarro**, GPL/free, self-hosted) models everything — stores, products/variations, orders, carts, promotions, customer profiles — as **Drupal entities**, so commerce shares one system with Drupal content/Layout Builder/Views/Search API. Its edge is content-heavy, custom-catalog, or unusual-checkout stores; the cost is a **Drupal/PHP dev build** (order bumps/upsells and much else are custom or contrib, not turnkey). **Not a Merchant of Record** — you own VAT/tax; for global tax handled, see `/sales-merchant-of-record`.
- **Headless via core JSON:API + the Commerce Cart API module**: back-office data is read/written through Drupal core **JSON:API** — `/jsonapi/{entity_type}/{bundle}` (e.g. `/jsonapi/commerce_product/default`, `/jsonapi/commerce_order/default`), **UUID-addressed**, `application/vnd.api+json`, **no PUT** (PATCH to update), filter/`include`/sparse-fieldsets, and **`page[offset]`/`page[limit]` offset paging** (default ~50). The buyer flow (cart/checkout) needs the contrib **Commerce Cart API** module (**cart token**, add/update/remove items, checkout) with the **`Commerce-Current-Store`** header for multi-store. Prices are `{number, currency_code}` objects.
- **The add-to-cart permission footgun**: adding an item via **raw JSON:API fails unless anonymous users can *administer stores*** — a security hole; **don't grant it**. Use the Commerce Cart API + cart token instead. Auth is contrib: **Simple OAuth** (Bearer from `POST /oauth/token`, password/client_credentials), Basic (basic_auth), or JWT; **configure CORS** for browser consumers. **401 = bad/missing token; 403 = authenticated but the Drupal role lacks the per-permission access** (grant the specific permission, don't over-permission).
- **Outbound events via the Commerce API module or a Drupal event subscriber**: core Drupal has **no webhook-URL screen** — the **Commerce API** module emits **order state-transition webhooks**; otherwise react in code to `commerce_order.place.post_transition` / `OrderEvents`, or use the contrib **Webhooks**/Rules module. Treat deliveries as hints: re-fetch the order by UUID, dedupe, and keep a polling reconciliation backup. **Platform skill**: `/sales-drupal-commerce`.
- **Best for**: agencies and technical teams building a content-driven or highly-customized store on Drupal who have PHP/Drupal devs. For the WordPress-plugin equivalent compare `/sales-woocommerce`; for a mid-market PHP/Symfony platform, `/sales-shopware`; for GraphQL-native or Node/TS headless stacks, `/sales-saleor`/`/sales-medusa`; for turnkey hosted SaaS, `/sales-shopify`/`/sales-bigcommerce`.
